# Praxis

**A governed AI delivery team, encoded as a Claude Code plugin.**

Praxis turns a single AI coding tool into a full delivery org: 17 role agents
(PM, architect, security, QA, SRE, and more) draw on 91 disciplined skills
through 9 workflows, gated by 17 governance checkpoints with evidence packs —
so requirements, architecture, and releases get principal sign-off, not
silent auto-approval. Agents route to models by capability tier (not
hardcoded names), so cost scales with task difficulty across 8 supported
harnesses. Once a slice has run cleanly by hand, drive mode lets the loop
keep going between gates — budget-capped, sandboxed, telemetry-logged. And
the library measures its own usage: three telemetry layers feed a
self-review cadence instead of guesswork. Counts are generated by
`scripts/build-registry.py` and CI-checked.

> **Status:** Early release (`0.1.0`) — actively maturing against real projects and open for external use. Stable enough to use on your own projects today; some interfaces may still shift as it hardens. **Harness support:** tested end-to-end on real engagements on Claude Code and Codex; the other six adapters (Gemini CLI, Cursor, OpenCode, GitHub Copilot, Kiro, Antigravity) are shipped and structurally validated (installer + CI cover them) but not yet exercised end-to-end on a real project — see the status column below.

**Get started in 5 minutes:** [`docs/quickstart.md`](docs/quickstart.md) — install, verify, run `/discover` on a toy idea, see what lands in `.project/`.

## Installation

Four paths. Pick the one that matches your tool + workflow.

### Path 1 — Plugin-dir loading (recommended for first test)

The library is structured as a Claude Code plugin. Point Claude Code at the directory directly — no copying, no install.

```bash
# Clone or download the library
git clone https://github.com/jeet129/praxis.git ~/dev/praxis

# Launch Claude Code with the library loaded as a plugin
cd ~/dev/your-test-project
~/dev/praxis/try-as-plugin.sh --init .
```

The bundled `try-as-plugin.sh` validates the library + Claude CLI, creates the `.project/` memory tree if `--init`, and runs `claude --plugin-dir <library>`. Library updates propagate immediately — no re-install.

### Path 2 — Codex plugin marketplace

Codex users should install the generated Codex plugin package:

```bash
codex plugin marketplace add jeet129/praxis --sparse .agents/plugins --sparse plugins/praxis-codex
```

Then open Codex:

```text
/plugins
```

Install `praxis-codex`, then start with `$praxis-setup-subagents` and `$praxis-start`.

The Codex package is generated at `plugins/praxis-codex/` from the canonical root library plus Codex-specific command skills and subagent profiles.

### Path 3 — File install (8 supported tools)

The bundled `install.sh` copies the library into a target project in the right layout for any of 8 AI coding tools:

```bash
cd ~/dev/praxis

./install.sh --tool=claude-code /path/to/your-project    # default
./install.sh --tool=cursor      /path/to/your-project
./install.sh --tool=gemini      /path/to/your-project
./install.sh --tool=opencode    /path/to/your-project
./install.sh --tool=copilot     /path/to/your-project
./install.sh --tool=kiro        /path/to/your-project
./install.sh --tool=antigravity /path/to/your-project
./install.sh --tool=all         /path/to/your-project    # all 8 layouts side-by-side
```

Flags: `--dry-run` preview · `--force` overwrite · `--user` Claude Code user-global install · `--skip-memory` skip `.project/` tree creation.

Status: Claude Code and Codex are tested end-to-end on real engagements. The
other six adapters (Cursor, Gemini CLI, OpenCode, GitHub Copilot, Kiro,
Antigravity) are shipped and structurally validated — the installer writes
their layout and CI checks it — but not yet exercised end-to-end on a real
project. Feedback welcome; see the per-tool setup guide for the exact status
banner.

Per-tool setup notes live in [`docs/<tool>-setup.md`](docs/).

`./install.sh --tool=codex` remains available as the legacy `.team/` + `AGENTS.md` copy-based setup, but the plugin marketplace path is preferred for Codex distribution.

### Path 4 — Claude Code marketplace install (when published)

Once this repo is public on GitHub, Claude Code users can install via the marketplace:

```
/plugin marketplace add jeet129/praxis
/plugin install praxis@praxis
```

The marketplace manifest at `.claude-plugin/marketplace.json` is wired to this repo.

### Full installation playbook

For step-by-step installation, sanity checks, troubleshooting, and a "first 30 minutes" walkthrough, see [`INSTALLATION.md`](INSTALLATION.md).

## Quick start

Once installed, in Claude Code:

```
/start
```

The Delivery Planner agent walks you through ~10 questions about your project — mode (greenfield / brownfield), data plane, ML, agentic AI, compliance regimes, scale targets, stack, cloud. It writes `.project/semantic/project-charter.md` and tells you which governance gates apply.

Then for greenfield:

```
/discover     → Phase A: Product Manager + requirements_freeze gate
/architect    → Phase B: Solution Architect + Architecture Challenger + architecture_sign_off gate
/slice        → Implementation slice (repeat per slice on the roadmap)
/release      → production-release workflow + production_go_live gate
```

For brownfield: `/audit` first (codebase comprehension + arch reconciliation + debt audit + impact analysis), then `/discover`.

Quarterly: `/steward` for the System Steward's library review (skip until you have telemetry).

For the full operating guide, see [`PLAYBOOK.md`](PLAYBOOK.md).

## What this is and isn't

### What this is

- A structured discipline for AI-augmented software delivery, encoding what senior engineers do.
- A library that activates conditionally — a small greenfield Node API project triggers ~91 SKILLs; an ML-heavy regulated SaaS triggers ~50.
- Tool-portable — same content addresses 8 AI coding tools; 2 (Claude Code, Codex) are tested end-to-end, the other 6 adapters are shipped and structurally validated but not yet run on a real engagement.
- Patterns + scaffolding for the full lifecycle, not just the coding part.

### What this isn't

- An autopilot. You're the principal; the agents do the writing; you do the judgment.
- Fully self-improving. Telemetry is now wired (PostToolUse tap → `factory-record.sh`), but the quarterly synthesis (System Steward reading the metrics + proposing lifecycle changes) is still a manual cadence. Data is being collected; the review loop closing on real telemetry is imminent, not automated yet.
- A replacement for engineering judgment. The agents need a thoughtful human; mistakes compound otherwise.
- Battle-tested yet. It's an early release — validated against the kinds of projects it was designed for, but not against many real ones so far.

## How it works — architecture at a glance

Four layers from invocation to evidence:

```
WORKFLOWS — named compositions (greenfield-api-service, brownfield-enhancement, ...)
       orchestrate
AGENTS — role personas (delivery-lead, product-manager, solution-architect, ...)
       consume
SKILLS — 91 SKILL.md bundles (the disciplines)
       produce evidence for
GOVERNANCE — 18 gates (6 core + 12 conditional) with evidence packs + approver matrix
```

Two-tier orchestration: **Delivery Lead routes phases → Phase Leads run their phase → Specialists execute slices.** Cross-cutting agents (Code Reviewer, Security Reviewer, QA Engineer, Tech Writer, System Steward) gate.

The YAML files under `workflows/` are declarative specs, not a deterministic
execution engine — `delivery-lead` (an LLM agent) reads them and interprets the
steps, decision nodes, and gate wiring at runtime. Predicates like
`nfr_satisfied` or `slice_acceptance_met` are enforced by agent discipline and
the governance gates, not by a parser evaluating boolean expressions. That's a
deliberate tradeoff for now — a deterministic workflow linter that validates
step references and decision-node wiring statically is on the
[roadmap](ROADMAP.md), not yet built.

For the big-picture diagrams (operating model, layer stack, drive loop, slice lifecycle), see [`docs/operating-model.md`](docs/operating-model.md). For the lifecycle visualization, see [`docs/lifecycle.md`](docs/lifecycle.md). For the front-door routing logic, see [`skills/using-praxis/SKILL.md`](skills/using-praxis/SKILL.md).

## Model routing & cost

Agents don't hardcode model names. Each agent declares an abstract
`capability_tier` (`deep | standard | light`) in its frontmatter — `deep` for
adversarial judgment, architecture, and security work where misses are
expensive; `standard` for implementation and artifact generation; `light` for
mechanical/formulaic work like scaffolding and doc drafts.

`governance/model-routing.yaml` is the **single file** that names concrete
models per harness — Claude Code (`opus` / `sonnet` / `haiku`), Codex
(`model_reasoning_effort: high` / `medium` / `low`), Gemini CLI
(`gemini-2.5-pro` / `-flash` / `-flash-lite`). `scripts/apply-model-routing.py`
applies that mapping, rewriting `agents/*.md` frontmatter and
`codex-plugin-assets/codex-agents/*.toml` (`--check` mode verifies they're in
sync, for CI). Adding a new model family or vendor is a one-file edit, not an
agent-by-agent rewrite.

At runtime, `delivery-lead` doesn't treat the static tier as fixed: it applies
the `adaptive-model-routing` rubric before each sub-agent spawn and may shift
the tier ±1 step based on task novelty, stakes, and prior failure. On gate
failure, it promotes one tier and retries once before escalating to a human.
Every routing decision is logged to `.project/telemetry/model-routing.jsonl`,
which is what makes cost-per-slice and tier-effectiveness reporting possible
in `factory-evaluation`.
