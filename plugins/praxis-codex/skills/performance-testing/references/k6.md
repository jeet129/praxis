# Performance Testing — Grafana k6

k6 is the recommended default load-testing tool: JS/TS test scripts, a Go-based high-throughput engine, native CI integration, and thresholds that act as pass/fail SLO gates rather than dashboards someone has to eyeball.

```

```

## Scenarios and executors

A test `scenarios` map lets you run several load shapes in one script — e.g., steady background traffic plus a spike — sharing the same VU pool or isolated per scenario.

```javascript
// perf/scenarios/checkout-load.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    steady_state: {
      executor: 'constant-arrival-rate',
      rate: 200,                 // 200 iterations per timeUnit
      timeUnit: '1s',
      duration: '10m',
      preAllocatedVUs: 50,
      maxVUs: 200,
    },
    spike: {
      executor: 'ramping-arrival-rate',
      startRate: 200,
      timeUnit: '1s',
      stages: [
        { target: 200, duration: '1m' },
        { target: 2000, duration: '30s' },  // spike
        { target: 200, duration: '1m' },
      ],
      preAllocatedVUs: 100,
      maxVUs: 3000,
      startTime: '10m',            // runs after steady_state completes
    },
    soak: {
      executor: 'constant-vus',
      vus: 30,
      duration: '2h',
      startTime: '11m30s',
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<300', 'p(99)<800'],
    http_req_failed: ['rate<0.01'],
    checks: ['rate>0.99'],
  },
};

export default function () {
  const res = http.post(
    `${__ENV.BASE_URL}/v2/checkout`,
    JSON.stringify({ cartId: 'cart-123', paymentMethod: 'card' }),
    { headers: { 'Content-Type': 'application/json' } }
  );
  check(res, {
    'status is 201': (r) => r.status === 201,
    'has order id': (r) => JSON.parse(r.body).orderId !== undefined,
  });
  sleep(1);
}
```

**Executor choice by intent:**
- `constant-arrival-rate` / `ramping-arrival-rate` — fix *throughput* (requests/sec), let VUs scale to hit it. Use for SLO validation ("can we sustain 200 rps at p95<300ms").
- `constant-vus` / `ramping-vus` — fix *concurrency*, let throughput fall out. Use for capacity/soak tests where the question is "how does the system behave under N sustained concurrent users."
- `per-vu-iterations` — each VU runs a fixed iteration count. Use for deterministic comparison across runs.

## Thresholds as SLO gates

Thresholds are the pass/fail contract — they mirror the NFR targets from `nfr-definition`, not arbitrary numbers picked at test-authoring time.

```javascript
export const options = {
  thresholds: {
    http_req_duration: ['p(95)<300'],           // fails the run if breached
    'http_req_duration{scenario:spike}': ['p(95)<600'],  // per-scenario threshold
    http_req_failed: ['rate<0.01'],
    'group_duration{group:::checkout flow}': ['p(95)<1500'],
  },
};
```

`abortOnFail: true` on a threshold stops the test early on breach, saving CI minutes on a load test that's already failed:

```javascript
thresholds: {
  http_req_failed: [{ threshold: 'rate<0.01', abortOnFail: true, delayAbortEval: '10s' }],
},
```

## Browser vs protocol testing

- **Protocol-level** (`k6/http`) — the default. Fast, cheap, high VU counts (thousands), tests the API/service layer directly. Use for load, stress, soak, and spike tests.
- **Browser-level** (`k6/browser`, real Chromium) — use sparingly, for the handful of critical user journeys where render/JS/network waterfall matters (Core Web Vitals under load). Expensive per-VU; never run at protocol-test VU counts.

```javascript
import { browser } from 'k6/browser';

export const options = {
  scenarios: {
    ui: {
      executor: 'shared-iterations',
      options: { browser: { type: 'chromium' } },
      vus: 5,
      iterations: 10,
    },
  },
  thresholds: {
    browser_web_vital_lcp: ['p(75)<2500'],
    browser_web_vital_cls: ['p(75)<0.1'],
  },
};

export default async function () {
  const page = await browser.newPage();
  try {
    await page.goto(`${__ENV.BASE_URL}/catalog`);
    await page.waitForSelector('[data-testid="product-grid"]');
  } finally {
    await page.close();
  }
}
```

## Test data

Load once, share read-only across VUs — avoids re-parsing per-VU and memory blowup at high VU counts.

```javascript
import { SharedArray } from 'k6/data';

const users = new SharedArray('users', function () {
  return JSON.parse(open('./data/users.json'));
});

export default function () {
  const user = users[Math.floor(Math.random() * users.length)];
  // ...
}
```

## CI integration

```yaml
# .github/workflows/perf.yml
name: Performance
on:
  schedule: [{ cron: '0 3 * * *' }]   # nightly, not per-PR — load tests are expensive
  workflow_dispatch: {}

jobs:
  k6-load:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: grafana/setup-k6-action@v1
      - name: Run load test
        run: k6 run perf/scenarios/checkout-load.js --out json=results.json
        env:
          BASE_URL: https://staging-api.example.com
      - name: Upload results
        uses: actions/upload-artifact@v4
        with: { name: k6-results, path: results.json }
```

Run performance tests on a schedule or pre-release against a stable staging environment — not on every PR (too slow, and noisy neighbors on shared CI runners produce false threshold breaches).

## Result trending

Stream results to a time-series backend rather than reading a one-off JSON file — trend detection (p95 creeping up release over release) is the actual value, not any single run's pass/fail.

```bash
# Push to Grafana Cloud k6 (managed) or self-hosted via the Prometheus remote-write output
k6 run --out prometheus-rw=http://prometheus:9090/api/v1/write perf/scenarios/checkout-load.js

# Or output to InfluxDB / Grafana Cloud k6 directly
k6 run --out cloud perf/scenarios/checkout-load.js
```

Dashboard the trend in Grafana alongside the `observability` stack's service dashboards — regressions correlate with deploys.

## Common violations to flag in review

- No thresholds defined — a load test without thresholds is a script, not a gate.
- Threshold numbers invented ad hoc instead of pulled from `nfr-definition`'s targets.
- `sleep()` omitted entirely — unrealistic request pacing that doesn't model real user think-time.
- Running browser-level tests at protocol-test VU counts (resource exhaustion, misleading results).
- Load tests run against production without an agreed maintenance window and rate-limit awareness.
- Test data hard-coded inline instead of `SharedArray`-loaded (memory blowup at scale).
- No CI integration — perf tests that only run manually get skipped under deadline pressure.
