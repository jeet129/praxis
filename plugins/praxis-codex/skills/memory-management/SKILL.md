The read side of `.project/`. Where `project-memory` writes, this skill indexes, retrieves, and compacts. Together they keep project memory usable past the 500-entry mark where naïve filesystem lookup falls apart.

## When this skill fires

- An agent enters a phase and needs to read relevant prior memory — *not the whole directory*, just the slice relevant to its task.
- An ADR is being considered and the SA needs to check what prior decisions might be relevant (impacted same domain, superseded by anything, related by tag).
- An incident is being triaged and operational memory needs lookup by service, by date, or by similar past incidents.
- `working/` entries age past slice boundaries and need compaction to `episodic/`.
- `episodic/` entries age past their relevance window and need summarization into compressed forms.

## The memory hierarchy

Four layers, from what every session sees to what is only searched (after
Anthropic's "Components of agent memory", 2026):

| Layer | In Praxis | Size rule |
|---|---|---|
| Injected context | session-start banner: charter, the **memory map** (`praxis-memory map`, ≤ 40 lines), active workflow | `budgets` in `memory-layout.yaml`; push detail down, leave a link |
| Index | `.project/INDEX.yaml` + `.project/index/<kind>.yaml`, generated | regenerate, never hand-edit |
| Notes | the `.project/` kinds (paths from `memory-layout.yaml`) | one fact or decision per note, ≤ 32 KB |
| Event log | git history, `.project/telemetry/*.jsonl`, praxis-verify summaries | machine-written, searched not read |

## The index

Generated by a script, not maintained by the model:

```bash
.project/local/bin/praxis-memory index    # writes .project/INDEX.yaml and .project/index/<kind>.yaml
```

It reads each note's frontmatter where present and falls back to the folder,
the filename date and the first heading, so legacy notes are still indexed.
Run it after a batch of writes, at slice close, or from the heartbeat.

### Per-kind index format

```yaml
# .project/index/adr.yaml (generated)
kind: adr
path: ".project/decision"
entries:
  - path: ".project/decision/adr-0001-multi-tenancy-pool-model.md"
    title: "Use pool model for tenant isolation"
    type: "decision"
    date: "2026-02-14"
    tags: ["tenancy", "isolation"]
    domains: ["billing", "auth"]
```

### Top-level aggregation

```yaml
# .project/INDEX.yaml (generated)
counts: {adr: 42, semantic: 18, procedural: 7, episodic: 156, review: 30, incident: 23}
by_tag:
  "tenancy": [".project/decision/adr-0001-...md", ".project/episodic/2026-03-02-slice-12-close.md"]
by_domain:
  "billing": [...]
```

## Retrieval queries

The skill exposes a small set of query patterns the orchestrator and agents call. Each returns a *digest* (titles + paths + frontmatter) rather than full content — the caller fetches full content for the entries it actually needs.

### Query patterns

**By topic/tag.**
```
query: tags=[tenancy]
→ all entries tagged 'tenancy', ranked by recency
```

**By domain.**
```
query: domain=billing
→ all entries impacting billing, grouped by subtree
```

**By relationship.**
```
query: supersedes=adr-0001
query: superseded_by=adr-0001
query: related_to=adr-0001
→ entries in the supersession or related-by chain
```

**By time window.**
```
query: subtree=operational, since=2026-01-01
→ all incidents/postmortems since the date
```

**Combined.**
```
query: subtree=decision, tags=[tenancy, isolation], domain=auth, confidence>=medium
→ filtered intersection
```

### Result shape

```yaml
results:
  - id: adr-0001-multi-tenancy-pool-model
    title: "Use pool model for tenant isolation"
    path: .project/decision/adr-0001-multi-tenancy-pool-model.md
    excerpt: <first 200 chars of body>
    relevance_score: 0.91   # for ranked queries
  - id: ...
```

The agent reads the path for the entries it wants in full; this skill never returns full bodies in the digest. Keeps query results small.

## Reading memory

Read the map, then only what the task needs: the index entries for its tags or
domain, then those notes in full. Treat a note as a claim with a date, not as
ground truth: when a note drives a decision and it describes the system (a
path, a command, a provider, a version), check it against the code first, and
correct the note if it is wrong.

**Light-tier agents** (`capability_tier: light`, or any agent the delivery-lead
routed down to light) get this instruction explicitly, because smaller models
often skip memory and act on their first theory (see
`references/memory-read-protocol.md`): read the memory map and the relevant
notes *before* answering, and test a hypothesis against the code before acting
on it.

## Consolidation (offline, between sessions)

Memory degrades unless something prunes and re-checks it. Two halves:

**Mechanical — `praxis-memory consolidate`** (dry run by default, `--apply` to act):

- working notes of closed slices → `episodic/archive/slices/<id>/`
- working notes no open ledger refers to, untouched for `working_stale_days` → `episodic/archive/working/<month>/`
- earlier review rounds of a topic (newest kept) → `reviews/archive/<topic>/`
- closed inbox entries → `episodic/archive/inbox-closed.md`
- parallel-lane notes (`working/lanes/<lane>/`, `append_to:`) merged into their targets
- evidence runs past retention pruned from the gitignored store

It only moves notes (with `git mv` when tracked) and writes a record plus an
old→new path map to `operational/memory-maintenance/`. It never deletes a note.

**Judgement — the model-side pass** (`praxis-memory consolidate --print-prompt`,
run headless on a standard-tier model): re-check every fact in the injected
layer against the code, merge duplicates, promote recurring lessons to
`procedural/` or to a diff-triggered check, demote stale assumptions, fix
broken links. It outputs one patch for a human to review; it does not commit.

Cadence: after each slice closes, and weekly from the heartbeat for active
projects. Focus the model pass on volatile facts (infrastructure, commands,
owners) and on notes read most often.

### Operational and decision: never compact

ADRs, incident records and risk acceptances are append-only. Corrections are
added as dated amendments; consolidation never archives or rewrites them.

### Raw evidence is not memory

Logs, JUnit XML, dumps and screenshots belong in `.project/local/` (gitignored).
`praxis-memory check` warns when they appear in memory folders and
`praxis-memory migrate-local` moves them out.

## Mode handling (G/B)

**Greenfield.** Start with empty indexes; build up as `project-memory` writes accumulate.

**Brownfield.** If `.project/` is being introduced to an existing project, this skill does a one-time bootstrap pass — scan everything in `.project/`, build the indexes from the frontmatter. If entries lack frontmatter (legacy ADRs converted from older formats), tag them `confidence: low` and add them to the index with whatever metadata can be inferred.

## What this skill does not do

- Write entries. That's `project-memory`.
- Decide what gets compacted when — the policy is in the skill body above; the *execution* is here.
- Cross-project memory. Each project has its own `.project/`.
- Embedding-based semantic search. The index is keyword + structured-metadata only. If semantic search becomes necessary, that's a future extension (the index file format is forward-compatible).

## Common rationalizations

| The agent's thought | Counter |
|---|---|
| "I'll grep for what I need." | Grep finds matches; it doesn't find what you didn't think to search for. The index surfaces related entries. |
| "Reading the whole `.project/` tree is fine." | At 50 entries, fine. At 500, untenable. The index is the scale-out path. |
| "Memory is for archives; live work is in head." | What's in head at session end is lost at session end. Live memory through `.project/` survives. |
| "I'll skip retrieval; just write." | Writing without first checking for existing memory creates duplicates, divergence, and forgotten prior decisions. Read first. |
| "I'll hand-edit the index." | It is generated. Run `praxis-memory index`; edit the note, not the index. |
| "The note says it, so it's true." | Notes go stale as the system changes. Check a note that drives a decision against the code, and fix it if it is wrong. |
| "Compaction is premature optimization." | Without it, working/ grows to thousands of entries and every session pays for it. Run `praxis-memory consolidate` at slice close. |

## Verification

You are done querying memory when:

- [ ] Query specified by topic / domain / type / time range (not just "find stuff").
- [ ] Returned entries are scored by relevance, not just date.
- [ ] At least one entry was read end-to-end (not just title-scanned).
- [ ] No surprise hits — if the query surfaced an entry the agent didn't expect, that's investigated.

You are done consolidating memory when:

- [ ] `praxis-memory consolidate` was reviewed as a dry run, then applied.
- [ ] The model-side pass's patch was reviewed by a human (never auto-committed).
- [ ] `praxis-memory check` reports no broken links and the injected layer is within budget.
- [ ] `praxis-memory index` was re-run.

Evidence to check:
- Query latency stays under 1 second even at 1000+ entries.
- A new joiner can use the index to navigate without prior knowledge.

## Performance characteristics

The index is a flat YAML file. At 1000 entries the index is ~200 KB — trivially fast to load and search in any process. At 10,000 entries it's ~2 MB — still fine for in-memory query. Beyond that, paginated subtree indexes plus a top-level summary keep query latency bounded. We are not building a database; we are building a discoverable filesystem.
